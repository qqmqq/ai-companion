# 定时提醒没建成却回「我会提醒你」——根因与修复

日期：2026-09-17 ・ 来源：微信真实对话（惠惠 2026-09-17 02:36）

## 1. 现象

```
用户：明天提醒我去开会
角色：……几点？（明天你在家还是要上班，我都不知道。）
用户：今天大概中午12点吧，提醒我去行政楼交材料
角色：……好。好的，今天 12:00 我会提醒你：「去行政楼交材料」。
```

后台既没有 scheduled_jobs，也没有 work_tasks —— 提醒根本没建，角色却报了具体时间。

## 2. 取证（不是猜的）

- 数据库：`scheduled_jobs` 最新一条停在 16:43，18:36 这一轮**一行都没有**；`work_tasks` 全表为空。
- 后端日志（当时代码实例 17:23–18:39）：两条消息各有一条 `intent detected … intent:"none"`；`intent.detected` 之后直接进入回复生成，**没有任何建任务的步骤**。
- 用真实模型（deepseek-flash）复现同一个句子，原始输出是**空字符串**；在同一提示词下把输出上限从 200 提到 800/2000，立刻返回了完整 JSON：
  `{"intent":"schedule_message","when":{"kind":"clock","day":"today","hour":12,"minute":0},…}`；
  200 上限时另一次返回的是**半截 JSON**（`…"minute":`，`finishReason=length`）。

## 3. 根因（两个独立缺陷，缺一不可成灾）

### 根因 A：解析不出来 = 静默当成"用户只是在闲聊"

`action-intent.ts` 里 `maxOutputTokens: 200`。这类"先想再答"的模型在 200 tokens 下会把 JSON 截断甚至吐空；
而旧代码把 `extractJson()` 返回 null 与模型明确回答 `{"intent":"none"}` **当成同一件事**，都走 `NONE`：
不重试、不报警、不区分，于是"用户提了要求、系统什么也没做"完全无声。

### 根因 B：假确认兜底只认相对时间，认不出钟点

`messaging-pipeline.ts` 的 `looksLikeSchedulePromise` 只匹配「几分钟后/稍后/待会儿 + 发你/提醒」这种**相对时间**说法；
角色那句是**钟点**说法（今天 12:00 我会提醒你），直接漏网。
而本该兜底的 `looksLikeSuccessClaim` 只在"动作失败"分支里用，这一轮压根没有动作，所以也没轮到它。

## 4. 修复

| 文件 | 改动 |
| --- | --- |
| `backend/src/core/services/action-intent.ts` | 输出上限 200 → 600；**只有"模型确实吐出可解析 JSON"才算一次可靠判断**：空输出/半截 JSON 自动重问一次（上限 1200）；两次都问不出来 → 返回 `needs_clarification`（把话问回给用户），绝不静默当成闲聊；新增 `intent.retry` / `intent_unparsed` 日志，带上 `rawLength` 与 `finishReason` |
| `backend/src/core/services/messaging-pipeline.ts` | `looksLikeSchedulePromise` 扩到三类说法：相对时间、**钟点**（今天 12:00 / 中午 / 晚上八点 + 提醒/发你/告诉你…）、以及只承诺「（到时候）会提醒你」；澄清提示词改成"这一轮没能确定要安排什么或什么时候"，不再假定用户没说时间 |
| `backend/test/integration/scheduled-message.test.ts` | 新增 5 个回归用例；并顺手修掉一处历史遗留的括号错位（父测试的收尾括号落到了文件末尾，导致后面 5 个用例全变成它的子测试、失败时无法归因） |

注意：**没有**把泛泛的「好的，我记住了」也算成承诺 —— 那会给正常聊天乱塞更正。这是回归测试抓出来的（第一次改动就踩了，已收窄）。

## 5. 验证

### 真实模型复跑（同一句话，各 3 次）

| 用户原话 | 修复前 | 修复后 |
| --- | --- | --- |
| 明天提醒我去开会 | 空输出 → none（什么都没做） | `needs_clarification` ×3 → 角色把时间问回来（正是它当时该做的） |
| 今天大概中午12点吧，提醒我去行政楼交材料 | 空输出 → none（提醒没建） | `schedule_message / today 12:00` ×3 → 会真的建出提醒 |

### 新增回归用例（全绿）

1. 第一次半截 JSON、第二次正常 → 真的建出 job，且只重问一次（`intentCalls === 2`）；
2. 第一次空字符串、第二次正常 → 同样建出来；
3. 两次都问不出结构 → 不建 job，但注入澄清要求（不静默）；
4. 模型明确 `none` → **不重问**（`intentCalls === 1`），普通聊天零影响；
5. 钟点假确认（真实事故原句）→ 追加「（这条定时请求没有真正建立，你可以再说一次。）」；
6. 不误伤：「……几点？」这类反问、以及「好的，我记住了」这类普通应声 → 不加更正。

## 7. 诚实说明

- **那条提醒本身没有补建**：修复只保证"以后同样的话会建"。要不要现在替你把「今天 12:00 去行政楼交材料」补上，等你说。
- 微信里那句「好的，今天 12:00 我会提醒你」已经发出去了，无法撤回；对话里就是那样。
- 根因 A 的证据来自我用真实模型复现同一句话：200 tokens 时确实会截断/吐空，提到 600+ 后稳定返回完整 JSON；这是复现，不是推测。
